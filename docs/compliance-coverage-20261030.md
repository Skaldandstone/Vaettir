## User workflow

Project creation and the standalone compliance page discover the same versioned public reference catalog and the current workspace's saved definitions. The public catalog contains 13 options, including music/performance rights and SOC 2. SOC 2 is a reference with no bundled licensed control set; the reviewer must supply applicable criteria. Search/category filters preserve selections, and saved identities are selected by ID rather than a matching name. The complete public starter definitions are shared through `packages/core/src/complianceReferences.ts`.

The music reference contains eight review prompts covering use and territory, composition and recording permissions, synchronization, performance, reproduction/distribution, license conditions and attribution, expiry/withdrawal, and retained evidence. These are review starting points, not a determination that a right applies or that a license clears a use. The reference distinguishes composition from sound recording; use, agreement, jurisdiction and evidence must be reviewed. Source links remain with the catalog, including the U.S. Copyright Office and BMI descriptions. No private license terms enter the public catalog.

After creating a project with compliance selections, the compliance page prepares a durable review in the original project/account/workspace context. The same flow is available later. It traverses active cases in stable pages of 200, reads titles/background/Given/When/Then/tags/structured actions and expected results/responses/shared procedures/existing mappings, and explains shared terms for the top five relevance suggestions per control. Reviewers can select other scanned cases. Nothing is selected automatically. Existing mappings, uncertain relevance, incomplete scans and missing-check proposals are distinct. Attachments, executions and private license documents are not analyzed.

Limits are explicit: at most 20 selected frameworks, 100 controls, 2,000 cases and a 6 MiB source preview. The review reports total, scanned, archived and omitted cases. A truncated scan cannot create missing-case proposals. Larger control sets require a smaller scoped framework; this candidate does not provide a control-range picker. Matching is deterministic lexical relevance, not semantic proof or a passed execution.

A reviewer selects mappings and edits proposed titles/prerequisites/actions/expected results plus required project case fields, saves the selection, then applies that saved digest. Cases remain `PENDING_REVIEW`; ordinary case approval, execution and compliance sign-off are separate. Saved reviews resume without repeating analysis. A lost apply response retains its original request and reads the durable receipt before retrying. Explicit transactional refusals permit a fresh review; transport ambiguity does not silently create a new request.

## Tenant ownership and legacy records

Public references materialize idempotently as immutable versioned copies in the selected organization. Custom create/control/import operations require a current human editor and project context. They write only that organization's framework. Framework ownership and public catalog identity are immutable. No existing global row receives an inferred owner based on its name, creator or activity.

Legacy global IDs and existing project-linked evidence remain intact. Unowned custom definitions are quarantined from new mappings and mutations. Their existing project-linked controls/evidence can be read. The test-plan risk suggestions also exclude unowned/foreign catalog gaps; case-control links and pending sign-off reads exclude foreign-owned control metadata. A responsible reviewer can create a new workspace custom definition and import explicitly reviewed criteria; this creates new identities rather than claiming the legacy record. Public built-in metadata remains discoverable, but unrelated global custom controls are not disclosed through scoped lists, coverage or exports.

## Durable authorization and application

Migration 110 adds organization/catalog ownership, source revision counters and `ComplianceReviewDraft`. Existing 109 columns, tables and privacy protections are preserved. The analysis snapshot and original actor/workspace/request binding are immutable; an applied receipt is immutable. Membership removal/role/seat changes, organization suspension, project transfer and actor binding changes revoke retained review authority. Restoring the former values does not revive it. Existing project transfer guards may prevent a transfer before revocation is needed.

Preview/save/read/apply lock and revalidate current organization, membership, project and native actor. Apply compares the reviewed digest and current source snapshot, including control/case/step/mapping/shared-procedure revisions and case-field schema/version. One transaction creates pending-review cases, original case versions, mappings, audit provenance and the receipt. Concurrent duplicates either reconcile the same receipt or receive an explicit transaction conflict; ambiguous writes are not automatically retried. No provider or model calls occur.

## Existing deletion and erasure workflows

Review receipts use a restrictive project foreign key. Guided project deletion explicitly counts these records and blocks removal; it cannot silently cascade through retained review history. The existing original-organization erasure preview and transaction explicitly count and remove owned review drafts, controls and frameworks. Unowned legacy definitions remain unclaimed. Foreign-project references refuse through restrictive foreign keys and roll back the whole erasure, preserving both tenants. Existing evidence retention, staff authorization, deletion receipts and privacy erasure rules remain in effect. Local tests exercise both successful synthetic erasure and the foreign-link refusal; no customer deletion has occurred.

## Recovery boundary: deployment hold

Schema/client compatibility is not old-application isolation. An isolated negative test using the original API68 image and original schema109 Prisma client on schema110 **confirmed** that its globally scoped list/coverage/control-write routes expose or mutate another synthetic tenant's definitions. Setting a recovery environment variable in that old image does not help because it has no gate. Neither API67 nor API68 is a safe compliance rollback after tenant-owned data has been written.

The minimal recovery source is this candidate's shared `assertComplianceAvailable` guard in `apps/api/src/services/complianceRecovery.ts`, applied by `complianceProcedure` in `apps/api/src/routers/compliance.ts` and the compliance-reading risk-suggestion handler in `apps/api/src/routers/testPlans.ts`, retained together with the accepted109 privacy/OAuth code. A recovery image built from this tenant-aware source must set `VAETTIR_COMPLIANCE_RECOVERY_MODE=disabled`. Every compliance query and mutation then fails before its input/database handler; records are retained. An unexpected nonempty value also fails closed; unset or `enabled` uses normal scoped behavior. This is an application-enforced gate in the new source, not a proposed flag for old code.

The guarded routes are: `catalog`, `loadReference`, `preview`, `reviewDraft`, `reviewDrafts`, `saveReview`, `applyReview`, `listFrameworks`, `createFramework`, `setFrameworkVisibility`, `importControls`, `createControl`, `controlCoverage`, `testCaseControls`, `mapTestCase`, `unmapTestCase`, `mappedTestCases`, `unmappedTestCases`, `exportReport`, `recordEvidence`, `listEvidence`, `signOffControl`, `listSignOffs`, `requestSignOff`, and `myPendingSignOffRequests`, plus `testPlans.suggestRiskAreas`. Legacy list/coverage/export and framework/control creation/import are the primary global-selector risks; guarding the whole router also prevents indirect mappings, evidence and sign-off paths.

Before activation, Main must build an immutable recovery image from the reviewed source, verify the gate on that actual image against retained synthetic tenant data on110, verify privacy freshness/erasure and the current OAuth protections, and record its digest and runtime configuration. Recovery must preserve schema110 and tenant data, not reverse ownership columns or delete records. This chat has not built or deployed that image, changed IAM/provider configuration, or accepted hosted behavior.

## Ordinary case review integration and mobile repair

Hosted validation found that applying a compliance proposal correctly created a mapped pending case, but ordinary review rejected every compliance mapping as unsupported. The follow-up extends ordinary review only for complete, explicitly tenant-owned mapped context. It does not alter stored mappings, autoapprove cases or relax evidence review.

Mapped cases use `CaseReviewSnapshot/v3`, with exact native mapping, control and framework definitions, their revisions, original organization/project/case identities and the native case compliance revision. Metadata ownership/count admission precedes private body materialization; 50 mappings, 64 KiB compliance context and the existing 512 KiB whole snapshot limits are enforced without truncation. Native row locks, complete JSON round-trip equality and the reviewed content hash remain required. Foreign, unowned (including legacy built-in), missing, oversized and unsupported evidence contexts refuse new decisions. Structural coverage is shown concisely; full definitions and identities remain in Mapping details.

Unmapped cases retain their original V2 projection. Disabled or unknown compliance recovery mode withholds mapped context and new mapped decisions, while unlinked ordinary reviews remain available. Current-authorized exact accepted decision recovery still occurs before projection admission, including older V2 requests. Control/framework revision and native mapping-source revision prevent a mapped review from becoming current again after source change-and-restore. Ordinary approval remains a distinct explicit action.
