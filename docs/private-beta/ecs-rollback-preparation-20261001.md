# ECS rollback preparation (source only)

SSE-136 / P10-08. Prepared October 1, 2026; no production configuration update or rollout.

The normal API/web release entrypoint now selects the requested commit's ECR image, not `latest`. Before registration it requires a single completed, running ECS rolling deployment, an ACTIVE predecessor task with matching commit/digest identity, and its recovery image still present in ECR. It retains predecessor service/task configuration, recovery-image metadata and candidate/update/result evidence in a unique local attempt directory. Retrieved secret values are never collected; task configuration may still contain sensitive metadata, so these files remain private under `.local/`.

The prepared service configuration enables the circuit breaker and automatic rollback, uses 100 percent minimum healthy and 200 percent maximum running tasks, and preserves existing alarms, bake time, reset behavior and failure thresholds. It does not change desired count, IAM, secrets, load balancers or the scheduled service window. Scaled-to-zero, concurrent/incomplete rollouts, nonrolling controllers and unverifiable predecessors fail closed before registration/update.

After the ECS stability waiter, the existing strict release guard checks that the service actually completed the requested candidate. A healthy rollback to the predecessor is a failed release, not success. The caller must retain the evidence, investigate candidate failures and run authenticated smoke checks before reporting delivery. This does not make incompatible database migrations safe: only backward-compatible migrations may accompany a release, and application rollback does not roll back customer data or schema.

[AWS circuit-breaker documentation](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/deployment-circuit-breaker.html) requires ECS rolling updates and a prior COMPLETED deployment for recovery. It detects deployment task-launch/health failures; it is not continuous application-level monitoring after deployment completion. Current configured thresholds are preserved, not tuned speculatively.

Validation: pure synthetic configuration/identity tests; real Bash release-script execution against an AWS replacement (successful candidate, waiter-success after rollback, unavailable recovery image and in-flight deployment); normal operations and restore regressions. Read-only production API32 metadata was used to render a prepared configuration. Installed AWS CLI output-skeleton generation failed on its own synthetic response's zero lifecycle-hook timeout; this was reproduced with an empty synthetic request, which does not contain that hook. Independent installed botocore input-model validation passed, including negative checks for missing service, a non-boolean circuit-breaker flag and an unknown configuration field. No UpdateService request was submitted. Source tests and schema validation are not an AWS failure-injection/rollback drill.

Production API automatic rollback remains disabled until a separately validated release/configuration change is applied. The existing completed API32 image is the automatic recovery baseline for a future candidate; previously preserved API31/web26 images are manual recovery references, not automatically the predecessor for every future release. Explicit live second-tenant/restricted-role sessions remain required for production isolation acceptance. No provider credentials, customer fixtures, invitations or client-source processing are authorized by this preparation.
